# Work -- Leader Brief

Use this phase after approving Alignment and authorizing the assigned worker's Work and Memory envelope.

Leader responsibilities:
- For an already-authorized independent publication outside a worker's inherited target, use `takode board approve-delivery-target` to bind the exact repository, published refs and SHAs to the current worker/Work occurrence. Follow `/port-changes` and its port-tracking reference; this records existing authority and never authorizes new publication or live-quest repair.
- Keep the board row in `WORKING` while the worker performs the authorized work.
- Alignment approval confirms the worker's understanding of the authorized scope and the intended Journey routing; by itself it does not promote worker findings, leader paraphrases, or proposed approaches into requirements. Follow the complete worker-context authority rule in the preloaded `leader-dispatch` skill.
- Name the Work assignee brief. When there is no new context, a short natural Work authorization is sufficient. When context is needed, add only genuinely useful facts the worker cannot already access and write them naturally rather than requiring a dedicated heading or empty marker. Do not restate generic phase duties, worker-derived findings, or likely implementation approaches. Avoid reintroducing phase-by-phase v1 routing.
- Work may include investigation, implementation, tests, self-review, approved execution, browser/E2E validation, Port/sync/push, and iterative fixes. Project-specific safety, permission, durable-data, shared-resource lease, cluster/job, credential, external-side-effect, verification, and no-force Git rules remain authoritative.
- Apply the authoritative design-to-implementation continuity rule in `takode-orchestration/quest-journey.md`. When design and build are one intended outcome, keep one quest and Work occurrence; a design checkpoint pauses rather than ends the accepted build.
- Separate access/authority safeguards from fidelity-changing payload transformations. Protected or private access alone is not evidence that payload content requires sanitation. A transformation is inside the approved envelope only when explicit user direction, project/repository policy, an approved contract, or concrete payload evidence supports it. If a newly discovered concern would materially change fidelity, scope, cost/runtime, validation gates, or acceptance criteria, pause at User Checkpoint unless existing policy or an approved contract already covers that exact change; evidence alone does not authorize the broader scope. Normal non-transforming safeguards remain mandatory.
- Keep validation and remediation bounded. Require approved checks, then allow one focused autonomous remediation pass per root-cause issue class plus its recheck by default unless the accepted contract requires more; group substantially related findings instead of treating each occurrence as a new class. Confirmed credential exposure, destructive risk, data loss, privacy violations, or material correctness failures remain blocking. If the recheck still fails materially, do not claim success or start another autonomous loop—report or escalate the blocker. Cosmetic or non-material issues should be delivered with a caveat. A new validator or hard gate introduced mid-Work needs existing contractual support or a User Checkpoint.
- This brief is the authoritative source for recovery routing inside an active Work occurrence.
- Recovery preserves the full remaining authorized Work envelope. After a system, transport, provider-stream, compaction, or leader-recycle interruption, recover the latest durable state and resume every still-authorized Work responsibility in one continuation instead of authorizing implementation, validation, commit, sync/push, approved preparation, or read-only preflight as separate micro-handoffs. Treat a status request as an update, not an implicit pause.
- For `recovery pending`, inspect progress once and allow one short verification window. If progress continues, let the same turn run. If no progress is evident, interrupt the stale turn and resume the same full remaining authorized Work envelope. Refresh volatile preconditions inside that envelope; verify rather than repeat completed side effects, and do not override Takode's exact-once replay proof or recovery suppression.
- If the worker needs authority or user judgment outside the approved envelope, keep the current Work occurrence paused at `USER_CHECKPOINTING` with linked needs-input. The leader records and applies the approved continuation and any approved scope change. When same-quest routing expands a previously design-only current quest to include implementation, reconcile the current quest metadata before returning it to Work: revise the title when it still reads as design-only, and update the description and TLDR when they no longer cover the full approved design-and-build scope. Do not defer this correction to final Memory. Update the remaining Journey only when needed, then return the current quest to its assigned worker in Work. Same-quest routing continues implementation; design-only or successor routing closes the current accepted scope before the guarded Work -> Memory transition.
- Do not routinely spawn embedded review phases. If independent review is genuinely needed, create a separate quest with its own Alignment -> Work -> Memory flow.
- Require the worker to keep one detailed Work phase note current. The final Work note should record outcome, key decisions, evidence, sync/external state, residual risk, checkpoint decisions, and Memory handoff. For tracked changes, it names the selected target and ordered target SHAs on a dedicated `Synced SHAs:` line.

Completion:
- The assigned and claimed worker may use the worker-owned Work -> Memory transition only after the current Work note exists, unresolved checkpoints are settled, and the quest remains within the approved authorization envelope. Every transition must supply exactly one fresh evidence mode: synchronized selected-target SHAs through `--commit` / `--commits`, or `--no-code` only for genuine zero-git-tracked-change Work.
- For an approved optional suffix `[work, user-checkpoint, memory]`, when Work proves the concrete skip condition, the worker may add `--skip-optional-checkpoint "<reason>"` to the guarded `work-to-memory` command; the board records the reason. Generic `board advance` remains blocked because that direct skip would enter Memory without the guarded evidence boundary.
- Required checkpoints and optional checkpoints that are actually taken must be followed by a later Work occurrence before Memory. Verify or revise the remaining suffix to `[user-checkpoint, work, memory]` before entering the checkpoint; after the user decision, generic advance may resume into that later Work, which applies the decision and owns the eventual guarded transition.
- Apply the lifecycle guide's delivery-evidence guard before telling the user a feature is implemented, available, or ready to test. When accepted scope still includes implementation or another evidence-bearing delivery, apply the same guard before Work enters Memory. A selected design alone is not delivery evidence.
- Treat a handoff with uncommitted changes, unsettled target sync/push, missing final verification, or missing structured target code commits as incomplete Work even if the worker says "Work complete"; route the same worker back to Work with the exact missing facts. A Work note or old quest commit list does not replace fresh transition evidence for the current occurrence.
- When the guarded transition reaches `MEMORY`, confirm tracked Work commits are already visible as structured quest metadata, then promptly report the main accepted answer, finding, or outcome from the Work note to the user. This report normally carries the substantive `:A:<ids>` answer: retrieve or reread every covered user message, follow the canonical answer-quality rule in `takode-orchestration`, and include the useful explanation, findings, uncertainty, recommendation, and next action. Do not withhold that report until final Memory closes, and do not describe the still-open quest as technically complete.
- In the same leader turn, read the Memory leader brief and send the Memory phase instruction to the normal same worker unless a documented exception requires another owner. The user-facing thread may be Ready once the accepted outcome is reported even while the quest remains open in Memory for mandatory durable closure. Do not send synchronized Work SHAs as a Memory delta merely so Memory can attach them.
- Missing project-tracked work or code-commit evidence returns to Work; final Memory may attach separate memory-repository commits but must not patch tracked implementation files or first-attach Work code SHAs.

When reporting an accepted tracked delivery, use the returned delivery ID with `quest commit-links q-N --delivery <id>` and place those exact chips beside the normal change explanation. A subset may be selected explicitly. Do not invent IDs, replace old response selections with the current quest list, or treat authoring links as commit-evidence publication. The existing message/thread owns when the change was introduced; full titles and Git-derived counts come from the recorded delivery.
